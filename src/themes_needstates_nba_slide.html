Need-state architecture

From Themes to Need States to Next Best Action

Each stage builds a graph over the previous stage's output — subcategories become Themes, purchase graphs become Need States, and Need-State journeys become the Next Best Action.

STAGE 1 · THEMES

Subcategory graph → Leiden → Themes

Every subcategory is a node. Edges connect subcategories using PPMI (pointwise mutual information) co-occurrence strength. Leiden community detection then clusters tightly-linked subcategories into Themes.

  • Node = one subcategory (catalog-wide)
  • Edge weight = PPMI between subcategory pairs
  • Leiden partitions the subcategory graph into Themes

STAGE 2 · NEED STATES

Basket graph → GNN embedding → Leiden

Inside a Theme, each household-week basket is its own graph: nodes are products bought together, edges are co-purchase strength. A GNN compresses each basket's graph into one embedding; plotting every basket in that feature space and running Leiden clustering yields Need States.

  • Node = one product, as it appears in one basket
  • Edge weight = co-purchase strength within that basket
  • GNN compresses each basket's graph to one embedding
  • Leiden clusters embeddings across all baskets → Need States

STAGE 3 · NEXT BEST ACTION

Lookalike journeys → Next Best Action

Households move between Need States week to week. A new customer's basket is embedded the same way and placed in this space; its nearest lookalike households reveal which journeys are common from here — surfacing the Next Best Action.

  • Same embedding space as Stage 2, plus each household's path across weeks
  • New basket embedded via the identical GNN path, placed in the space
  • Nearest lookalike households show plausible next journeys → the recommended action
